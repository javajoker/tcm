# @tcm/wuxing

Yin-yang / five-phase engine of the TCM app: **birth chart → element weights → generation/restraint
propagation → 大運 / 流年**, plus the seasonal and 五運六氣 priors that turn those numbers into a
personalised *reference panel* (what is "normal" for this person, now).

- Pure TypeScript, **zero runtime dependencies**, deterministic, no I/O, no system clock.
- Runs in the browser, Node and workers; the same code is meant to power the web app.
- Algorithm specification: [`docs/wuxing-algorithm.md`](../../docs/wuxing-algorithm.md).
  Read it first — every non-obvious choice (and every number) is explained there.

## Scope

Extracted and re-implemented from the author's earlier BaZi engine (fate4 @ `aba58ee`, private), taking **only**
the yin-yang/five-phase computation that combines birth data with the year: 排盤 (solar terms, true solar
time, four pillars, 人元司令, 大運), L1 weights, L3 propagation, and the 流年/大運 evaluation. Everything
else in that engine (十神, 旺衰, 格局, 用神, 神煞, 應期, 人格, 六爻/六壬/奇門, reports) is intentionally left out.

## Use

```ts
import {
  buildChart, buildBase, evaluateYear, innateProfile, buildReferencePanel, toJulianDay,
} from "@tcm/wuxing";

const chart = buildChart({
  year: 1990, month: 5, day: 12, hour: 14, minute: 30,
  sex: "male", timeZone: "Asia/Shanghai", longitude: 121.47,
});                                           // 庚午 辛巳 丁丑 丁未
const base = buildBase(chart);                // natal element shares after propagation
const innate = innateProfile(base);           // shares, relative deviation, bands, capped degrees
const year = evaluateYear(base, 2026);        // 流年 evaluation with neutral-year-corrected delta
const now = toJulianDay({ year: 2026, month: 10, day: 3, hour: 12, minute: 0, second: 0 });
const panel = buildReferencePanel(base, now); // innate + 流年 + 五運六氣 + 時令 → reference panel
```

Without birth data pass `null` instead of `base`: the innate and BaZi-annual blocks are omitted and the
panel is built from season and 五運六氣 only.

## Develop

```bash
pnpm install                          # once, at the repository root (workspace)
pnpm --filter @tcm/wuxing test        # node:test, runs .ts directly (Node ≥ 22.18 / 24 / 25, type stripping)
pnpm --filter @tcm/wuxing typecheck   # tsc --strict, noUncheckedIndexedAccess, erasableSyntaxOnly (tsconfig.base.json)
```

Sources use only *erasable* TypeScript syntax and `.ts` import specifiers so they run unbuilt under Node's
type stripping and bundle unchanged with Vite/webpack.

## Verification

| What | How |
|---|---|
| Parity with the original engine | `test/oracle.test.ts`: 10 births × (pillars, 司令, 大運, base weights, 5 annual evaluations), 168 solar-term instants, equation of time, ΔT — against vectors generated by running fate4 itself (`test/fixtures/fate4-oracle.json`) |
| Solar terms vs an external reference | `test/astro.test.ts`: all 240 Hong Kong Observatory terms 2019–2028 within 60 s (HKO publishes whole minutes) |
| Calendar anchors | 1949-10-01 = 甲子, 2000-01-01 = 戊午; day pillar advances one step per day over ~73,000 days |
| Engine invariants | order independence of propagation, mass non-increase, non-negativity, normalisation, L1 totals (468 / 368 / 130 / 110) |
| Classical tables | 歲運, 司天/在泉, 客氣 rotation, 大寒 year boundary |

## Limits (stated, not hidden)

- After 2050 ΔT is extrapolated: solar-term instants carry more than the 60-second tolerance.
- The element-weight model has calibrated-by-choice parameters (month command ×2.0, 司令 ×1.5, rounds = 3 …) and no
  clinical validation. The reference panel therefore caps every block and reports each one separately.
- Structure rewriting (合化刑沖害破) and 流月/流日 are not modelled.
